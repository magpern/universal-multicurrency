# ADR-0031: v1.0 release contract

**Status:** Accepted (Milestone 26, target v1.0.0)

**Related:** [`docs/M26_V1_READINESS_PLAN.md`](../M26_V1_READINESS_PLAN.md)
(full audit, work-package definitions, falsification matrix), ADR-0008
(version support policy), ADR-0009 (uninstall retention), ADR-0024
(third-party extension evidence model)

## Context

Twenty-five milestones (M0–M25) have shipped as releases v0.5.0 → v0.24.0, each
gated by a release-audit process, a five-leg CI matrix, and structural/
security/performance guard tests. The product owner asked, ahead of M26,
whether the plugin is ready to leave the 0.x series and become `v1.0.0` — to
be answered with repository evidence, not assumption.

`docs/M26_V1_READINESS_PLAN.md` records that audit in full: a capability
inventory reconstructed from source, a roadmap-completeness check (zero
`TODO`/`FIXME` in `src/`, no broken promise), a 34-area v1.0 product contract,
a known-limitations classification, and a persistence/schema audit confirming
`Settings::SCHEMA_VERSION = 7`, `OrderSnapshot::SCHEMA_VERSION = 5`,
`PersistedKeys::INVENTORY_VERSION = 10`, and no DB migration — all verified
directly against source, with zero undocumented persistence writes found.

**No category-A release blocker was found.** The gaps that exist are
documentation staleness (most visibly, `README.md` still describing v0.13.0),
a security-review narrative not re-audited since M8 (though the structural
guards that actually enforce it run continuously over the whole tree), a
thin Playwright suite (one spec), and a hardcoded hostname literal in a test
fixture that violates this repository's own no-site-names rule. None of these
are missing functionality; all are hardening/documentation work appropriate to
a terminal "harden, prove, document, release, close" milestone.

This ADR freezes that contract before implementation begins, so WP1–WP12 test
against an unambiguous, written bar rather than a moving target.

## Decisions

### 1. M26 is a hardening milestone, not a feature milestone

M26 adds no product feature. Everything in `docs/M26_V1_READINESS_PLAN.md` §14
is out of scope for this milestone regardless of how small the addition would
be: a REST write API for fixed prices, flat-markup bulk seeding, Quick Edit
fixed-price fields, custom switcher media/Library icons, additional
exchange-rate providers, per-currency provider selection, `country_change` geo
mode, gift cards/memberships, further extension adapters beyond the M19
priority set, full Bookings support, promotion of any extension's evidence
tier toward E3/Integrated, licensed premium extension code, mutation-scope
expansion beyond Diagnostics, a storefront/admin redesign, or a
general-purpose frontend test framework.

*Consequences.* Any implementation work that starts drifting into one of these
areas stops and returns to this contract. A defect found during falsification
(ADR §5 below) may still require a production-code fix — that is corrective
work, not new scope.

### 2. No missing promised core functionality — the roadmap is complete

`docs/ROADMAP.md`'s "Future milestones" section lists only items explicitly
declared out-of-scope in their originating milestone's ADR (0024, 0029) — none
is a broken promise. Repository-wide search for `TODO`/`FIXME`/
`not implemented`/`out of scope` finds zero hits inside `src/` (enforced as
release-blocking by RB14 in `RELEASE_AUDIT.md`).

*Consequences.* v1.0.0 does not need to implement anything new to be an honest
release. M26's job is to prove and document what already exists, not to close
a functionality gap.

### 3. Persistence and schema state are frozen as fact, not target

`Settings::SCHEMA_VERSION = 7`, `OrderSnapshot::SCHEMA_VERSION = 5`,
`PersistedKeys::INVENTORY_VERSION = 10`, no DB migration mechanism — confirmed
directly against `src/Settings.php`, `src/Order/OrderSnapshot.php`,
`src/PersistedKeys.php`, and a full grep of persistence primitives across
`src/`. M26 must not bump any of these values merely because this is v1.0.0. A
bump is permitted only if implementation or falsification work discovers a
genuine correctness defect requiring one — and any such discovery is treated
as a release-blocking event requiring re-audit before proceeding, not a quiet
schema change.

*Consequences.* The v1.0.0 upgrade story is: every existing schema-migration
step (0→1 … 6→7) already works; M26 adds fixture coverage for three previously
untested starting points (schema 2, 3, 5) and an operational rehearsal across
six published historical releases, without changing what a merchant's stored
data looks like after upgrading.

### 4. Third-party compatibility evidence tiers are preserved, not promoted

The E0–E3 evidence model (ADR-0024) and current tier assignments — Subscriptions/
Product Add-Ons/Bundles at E2 (Characterized), Composite Products/Bookings at
E0 (Not evaluated), no extension at E3 (Integrated) — remain exactly as they
are. v1.0.0 does not imply broader third-party support than v0.24.0 already
honestly claimed.

*Consequences.* No licensed premium extension code is obtained for this
milestone. `docs/COMPATIBILITY.md` may gain one clarifying sentence noting that
v1.0.0 does not change the evidence model, but no tier label changes.

### 5. The falsification matrix is the milestone's acceptance bar

`docs/M26_V1_READINESS_PLAN.md` §11 defines 32 falsification items (A–AF)
spanning migration integrity, no-double-conversion, Classic/Blocks parity,
Visitor Location precedence, rate-staleness health, transaction-path HTTP
isolation, bounded reporting, CSV defenses, compatibility-claim honesty, admin
authorization, REST boundaries, persisted-data completeness, migration
idempotency, version-metadata synchronization, production-guard integrity,
rollback semantics, documentation accuracy, and scope containment. Every item
must close green with cited evidence, or be honestly reclassified as an
already-accepted category-C known limitation, before `v1.0.0` is tagged.

*Consequences.* WP9 (Corrective review and falsification) is not optional
paperwork — it is the actual release gate. A falsification item that cannot
honestly close green blocks the release.

### 6. Roadmap completion language is written only after the release exists

`docs/ROADMAP.md`'s Milestone 26 entry is updated to reflect implementation
progress throughout M26, but its status stays **"release pending"** until the
`v1.0.0` tag exists, GitHub Release is published, and the artifact is
independently verified. The "Milestones M0–M26 complete" statement and the
conversion of "Future milestones" to "Backlog / Future enhancements" are
written exclusively as part of post-release closure — never earlier.

*Consequences.* At every point before release, a reader of `ROADMAP.md` sees
accurate state: a release candidate is not a release. No `M27` milestone is
ever created — future work moves to a Backlog, not another mandatory
milestone.
